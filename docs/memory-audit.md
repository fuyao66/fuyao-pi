# Memory / BCP 历史机制与生命周期审查

> **历史审查，不是当前缺陷清单。** 后续已交付摘要修订同步、压缩事件触发、统一来源校验及保守工作区隔离。精选记忆仍延期，向量扫描窗口和前缀长度限制仍存在。以下数字、探针与建议对应审查当时；当前行为见 [Billion Memory 当前文档](../packages/bili-memory/README.md)，完成状态见 [roadmap](memory-roadmap.md)。

审查基线：BCP `0.1.82`，fuyao-pi `27cad62` 后的 Memory 源码。本文是建议，不是已实施功能。
未修改生产数据库、删除摘要或重新生成真实向量。隔离临时库验证同步行为；本地规模只读聚合。

## 结论

先完善数据正确性与来源生命周期，再提高检索质量，最后考虑事实型长期记忆。
目前不需要按天自动硬删摘要，也不需要引入大型外部向量数据库。
BCP 的 T1/T2/T3 是压缩嵌套层级，不是短期/长期记忆；向量是摘要的派生索引，不是新知识。

## 当前结构

```text
Pi 原始 JSONL 会话（工具结果、消息、压缩调用；回溯证据）
  └─ BCP sidecar（模型写的摘要、覆盖消息 ID、父子块、active、tier）
       └─ Memory SQLite blocks + FTS（跨会话摘要副本及关键词索引）
            └─ memory_vectors（当前或旧 namespace 的派生向量）
```

Memory 不负责压缩、不默认复制全部工具日志；memory_expand 默认关闭。
BCP 会在模型请求视图中隐藏原文，不从原始 JSONL 删除这些消息。
迁移/备份应同时保存会话 JSONL、ACP sidecar，必要时还需祖先会话；Memory 数据库无法替代原始证据。

## BCP 实际机制

安装包根路径：`/home/fuyao/.pi/agent/npm/node_modules/billion-context-pi/`。

- 主对话模型在 `compress` 参数中自己写摘要，不是该工具再请求一个独立压缩模型。
  `dist/index.js:14867–14948` 处理参数并执行 kernel；`dist/index.js:5552–5576` 写入传入摘要。
- 目标可以是消息范围或旧摘要块范围。受保护工具、近期工作区、图片等可能被排除，工具调用/结果边界会调整。
  因此 `startRef/endRef` 不是完整覆盖证据；应使用 `directMessageIds/effectiveMessageIds`。
  参见 `dist/index.js:4331–4397,5489–5514,5577–5606`。
- 普通消息折叠生成 T1，块折叠提升层级并封顶 T3，记录 `directBlockIds`。
  被父块消费的子块置为 inactive，但旧摘要仍保留：`dist/index.js:5422–5444,5552–5574`。
- inactive 不等于过期或应删除，还可能来自分支/可见范围变化或 expanded 标记。
  `dist/index.js:1020–1081`。generation 的 young/old 也不是长期记忆分类。
- 同一 block ID 并非不可变：inline 恢复后符合条件的 refold 可以原地更新 summary/topic/runId。
  `dist/index.js:4754–4806`。这是 Memory 必须支持修订的重要依据。
- 解压依赖原始会话及祖先消息，默认文件输出，inline 是额外返回内容，不等于永久撤销压缩。
  `dist/index.js:15037–15060,15069–15282`。
- 0.1.82 有一项需注意的实现/说明差异：非 full 模式只用 active 子块摘要替换；正常已消费子块是 inactive，
  因而可能仍返回这些子块覆盖的原消息。不能假设默认解压一定只展开一层。
  `dist/index.js:2362–2395`。此为源码审查发现，未用生产会话做额外恢复实验。
- 摘要是模型生成的解释，不是已核实事实。来源引用、版本、用户原话与模型推断必须分开。

## 优先问题与证据

### P1／高：修订一致性（已复现）

`packages/memory/src/extension.ts:973–1022` 使用 INSERT OR IGNORE，已有记录只更新 msg_ids。
同 block ID 的 summary、topic、tier 等修改不会同步。

合成临时库实验：首次摘要 `OLD_MARKER`；源改为 `NEW_MARKER` 并改变引用；强制 rescan 后，
正文仍是 OLD、topic 仍是旧值，但 msg_ids 已指向新消息。删除源块后强制扫描，旧记录仍在。
这不仅检索旧知识，还可能让旧摘要与新的原文引用对应。BCP 原地 refold 证明此输入变化是合法路径。

建议：引入内容修订 hash、last_seen、source_state，事务性 UPSERT；保存必要的版本记录与引用对应关系。
同步更新 FTS（当前触发器主要处理插入/删除，需新增 UPDATE 处理），并使相关派生向量失效。
不要直接 REPLACE 导致主键更换/外键关系丢失；正常修订保留稳定内部 ID。

### P1：来源政策不一致（已由代码确认）

自动补建每批校验允许列表中的路径+格式，但关键词/向量搜索主要只按 project 过滤；
手动 backfill 只经整体 UI 确认，没有复用同一来源过滤。
因此停用来源不等于撤回历史索引，也不等于禁止所有路径上传。更重要的是：某块已从仍被允许的 sidecar 中移除时，
数据库保留该块且自动校验只到文件级，仍可能自动上传该旧块。手动上传虽有整体确认，不属于未经确认绕过，
但与用户对“停用来源”的直觉不一致。应把上传资格校验扩展到块及其当前修订，而不只检查文件。

证据：`packages/memory/src/extension.ts:1090–1144` 搜索条件、factory 内 uploadPermissions 和 embed backfill 分支；
`packages/memory/src/hybrid.ts:88–142` permissions 是可选参数。

建议：统一来源状态策略，明确暂停采集、禁止出站、归档、不参与搜索、永久删除的不同含义。
默认来源禁用后禁止自动/手动远程上传；已存记忆进入可见的停用/归档状态，默认搜索排除但允许用户显式查看。
文件一次消失不自动删除：记录 missing_since 并提示，允许迁移映射或恢复。

### P1：丢失 BCP 谱系（事实已确认，父子冗余风险尚未在本地出现）

`packages/memory/src/extension.ts:578–600` 不保存 active/directBlockIds 等信息。
父子块和不同分支可以同时命中；RRF 只按数据库行 ID 合并，不懂父子覆盖关系。
本地已有 14 条 inactive，但目前全为 T1，不能把这 14 条直接解释为 T2/T3 重复。

建议：保存 session identity、branch/source、parent-child edges、消息覆盖集合与状态。
召回时按谱系分组，同一组展示最相关版本；允许细节查询命中子块，不应仅保留最高层摘要。
同名不同路径项目需要稳定项目 ID；当前 basename project 可能串组。

### P1：容量上限导致新记忆被排除（源码确定，当前规模尚未触发）

`packages/memory/src/hybrid.ts:62–67` 按 b.id 升序 LIMIT maxBlocks，配置默认/上限 10000。
前 10000 条之外的新摘要不会因反复补建进入窗口；语义搜索也有前缀扫描上限。

建议：把每轮处理预算与库容量分开：按缺失/失效向量分页补建，持久游标/轮转不遗漏新项。
检索规模扩大后再选择 SQLite 向量索引或分区；不是简单调大常量或删旧摘要给新摘要腾位置。

### P2：长摘要尾部不可语义召回（设计局限）

`packages/memory/src/embeddings.ts:49–56` 只嵌入前 6000 UTF-8 字节。
尾部结论/约束/待办可能完全不参与向量召回；哈希也是前缀 hash，不代表整个摘要版本。

建议：保留独立的整篇 source_hash，再按段落/标题分 chunk，每块长度受限并保留 parent_id。
命中后按父摘要聚合，不让同一篇占据结果列表；批次、总费用均应有预算。
初期无需额外模型生成第二份摘要。

### P2：检索质量缺少测量

关键词与余弦各取候选，RRF=1/(60+rank) 合并，缺少 lineage 去重和验证集。
硬路径剥离有隐私收益但也会丢失精确代码定位；中文输入、版本号、同名项目应测试。
建议建立 20–50 个合成/用户批准案例：精确函数名、跨语言同义词、新旧决策冲突、尾部事实、项目隔离、无答案。
报告 Recall@k、重复率、错项目率、无关召回率、延迟/费用，再决定是否 rerank 或换 embedding 模型。

### P2：可选原文展开的取消与会话边界

`packages/memory/src/extension.ts:2001,2075–2096` 的 memory_expand 没有使用传入 signal，
也没有在异步读取完成后复查 session generation 和块修订。取消/切换后可能仍返回之前读取的原文。
目前该功能默认关闭，属于启用前应修复的边界。建议传播取消信号、返回前校验来源/修订与会话。
较长会话还受 32 MiB 读取上限影响；可考虑消息偏移索引，不应把没读到误报成原文已消失。

### P2：删除身份与 namespace 回收

删除墓碑键是 `(source_file, block_id)`，同一文件改名/复制后能再次入库；旧路径复用还可能误抑制新块。
所以“防普通 rescan 复活”不等于“永久遗忘”。清理需稳定会话身份、范围预览和迁移映射。
没有时间戳和未来时间戳的记录不会被常规按天 prune 删除，需要单独标注。

旧 namespace 不会因换模型自动删除。3072 维 float32 × 10000 条仅向量负载就约 117 MiB/namespace，
不含 SQLite/FTS；当前小库不紧迫，但多次换模型会累积。回收派生缓存比删知识更合理。

## 推荐的分层（职责，不是四份原文拷贝）

1. **证据层**：原始 JSONL+ACP sidecar，原地保存/备份；Memory 存稳定引用，不复制全量日志。
2. **事件/过程记忆层**：可追溯、可修订的 BCP 摘要，带项目、时间、状态、谱系。
3. **长期知识层（以后可选）**：已确认偏好、仍有效决策、约束、未完成任务；每条有来源和有效/被替代标记。
   不按普通访问时间淘汰，不自动把模型推断提升为用户要求；先人工 pin/确认，后考虑模型建议提取。
4. **检索派生层**：FTS、分块向量、查询缓存，可从上层重建，不另算事实来源。

当前真正实现的是证据引用 + 摘要副本 + 派生检索层，还没有独立的长期事实管理层。

## 清理和维护建议

| 对象 | 建议政策 |
|---|---|
| 旧模型 namespace、失效向量、可重建缓存 | 可定期预览回收；保留当前版本和短期回退版本 |
| 被覆盖或长期未用的过程摘要 | 归档、默认降权/不展示，可恢复；不能只按 age 永删 |
| 用户偏好、有效决策、项目约束、未完成任务 | pin，除非明确撤销/被新决定替代，否则长期保留 |
| 来源暂时丢失 | 标记 missing，停止出站，提供重新关联；不擅自删除 |
| 用户明确遗忘的内容 | 明确范围、确认、删除索引+向量+缓存/派生记录；说明原始日志/备份是否仍保留 |

当前 prune 是硬删除本地索引和关联向量，创建墓碑防止重新扫描复活；不删除原始会话。
时间按压缩块 created_at，不是最后使用时间/知识过期时间；未来时间戳记录即使执行 prune 0 也不会删除。
没有回收站，也没有现成恢复墓碑入口。
不要立刻默认自动 prune 30/90 天。可先每周生成维护预览，在 /memory 的维护页确认，而不是新增一批命令。

备份应使用 SQLite 一致性备份机制或停库备份，不只复制一个正在 WAL 模式写入的 .db。

## 推荐实施顺序

1. **正确性版本**：内容 UPSERT+FTS更新+向量失效；保存来源状态；统一出站/检索权限。
2. **召回版本**：谱系/修订去重；公平分页补建；长摘要分块；建立小评测集。
3. **治理版本**：pin、归档/恢复、维护预览、旧 namespace 回收、可选事实层。

每一步应有可回滚 schema 迁移与隔离回归，避免更改来源归属/过滤时无意扩大上传范围。
BCP 适配还应遵守 schemaVersion 契约：缺省按 v1，未知更新版本先隔离/提示，不静默按旧格式入库。
本轮仅提出审查结果，尚未实施上述改变。
